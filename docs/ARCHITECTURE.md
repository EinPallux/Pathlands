# Pathlands — Technical Architecture

The engineering spec for a 60 FPS, browser-native 3D ARPG that later becomes an MMO **without a rewrite**. Read together with `CLAUDE.md` (standards) and `docs/NETWORKING.md` (Phases 7–8).

---

## 1. Stack & Repo Layout

- TypeScript strict · pnpm · Vite · Three.js (WebGL2) · Vitest · Playwright.
- Client-only static deploy (Vercel) through Phase 6. Server workspace added in Phase 7.

```
src/
  main.ts               — boot, canvas, game loop host
  app/                  — screens/router (menu, char-select, in-game), settings, quality detect
  sim/                  — THE SIMULATION (deterministic, renderer-free — see §3/§9)
    ecs/                — archetype ECS core
    systems/            — movement, combat, ai, projectiles, buffs, loot, quests…
    rng.ts              — seeded RNG (the only randomness source in sim)
    commands.ts         — player intent types (the future network protocol, see §9)
  content/              — ALL game data: skills, affixes, items, monsters, zones, quests, loot tables
  render/               — Three.js layer: scene, camera rig, instancing, VFX, decals, post
  ui/                   — HUD + menus (DOM overlay), tooltip engine, input glyphs
  audio/                — WebAudio mixer, banks, positional emitters, music layers
  input/                — kb/mouse/gamepad → Command mapping
  save/                 — IndexedDB persistence, versioned migrations
  net/                  — (Phase 7+) protocol client, prediction/reconciliation
assets/                 — GLB/KTX2/WebP/OGG + MANIFEST.json (licenses)
tools/
  asset-gen/            — procedural asset generators (output → assets/)
  sim-bench/            — headless balance scenarios
  validate-content/     — schema + cross-reference validation (runs in CI/test)
server/                 — (Phase 7+) authoritative server workspace
```

## 2. Game Loop & Time

- **Fixed-timestep simulation at 30 Hz** (33.33 ms ticks), accumulator pattern; **render at display rate** with interpolation between the last two sim states for all transforms.
- Rationale: deterministic, cheap, and identical to the future server tick rate — client prediction in Phase 7 replays the same tick function.
- Visual-only continuous effects (particles, cloth-ish bones, UI) run on render time; anything gameplay-relevant runs on sim ticks only.
- Tab-hidden: pre-MMO the sim pauses; catch-up capped at 5 ticks to avoid spiral-of-death.

## 3. ECS (custom, archetype-based)

- Entities = ids; components = typed structs stored in archetype tables (SoA `Float32Array`/`Int32Array` columns for hot data: transform, velocity, health) for cache-friendly iteration and near-zero GC.
- Systems are pure-ish functions `(world, dt)` executed in a fixed ordered schedule:
  `input-commands → ai → movement/pathing → collisions → skills/projectiles → damage → buffs/dots → deaths/loot → quests/triggers → events-out`.
- **Events**: double-buffered event queues (`DamageDealt`, `EntityDied`, `ItemDropped`, `SkillCast`…). Renderer/audio/UI consume events + snapshot reads; they never mutate sim state directly.
- **Prefabs:** monsters/props/projectiles defined as component bundles in `content/`, spawned via a factory that resolves content refs once at load.
- Query API with cached archetype matching; component add/remove is deferred to end-of-tick (no mid-iteration invalidation).

## 4. Determinism Rules (enforced by lint + tests)

- All randomness via `sim/rng.ts` (PCG32, per-subsystem streams: combat, loot, generation). Snapshot-serializable.
- No `Date.now`, `performance.now`, `Math.random`, or any render/UI read inside `sim/`.
- Float determinism: single-arch (JS engine) determinism is sufficient — we require *replay* determinism (same seed + same command stream ⇒ same state hash), which is unit-tested every CI run with a scripted 1000-tick fight.
- Every entity-affecting input enters the sim as a **Command** (§9), even in single-player.

## 5. Rendering (Three.js, instancing-first)

- **Static world:** modular kit pieces rendered via `InstancedMesh` per (geometry, material) pair; zone chunks culled by a simple grid + frustum. Merged static colliders separate from visuals.
- **Skinned crowds:** monsters use skinned instancing (baked bone-texture animation / VAT — vertex animation textures generated by `tools/asset-gen`) so 100 enemies ≈ few draw calls per family. Hero player model gets a real skeleton for layered/blended animation.
- **Materials:** small custom shader library on `MeshStandardMaterial`-derived bases: rim-light term, hit-flash, dissolve-on-death, wind sway (vegetation), triplanar terrain blend.
- **Lighting:** one directional key (per-zone mood) + CSM-lite shadow for it, hemispheric ambient, small budget of point lights (torches, VFX) with distance-fade; lightweight baked/painted AO in kit textures.
- **Post stack:** bloom (selective by emissive), vignette, filmic tonemap + per-zone color-grade LUT, optional FXAA; damage/low-health screen-edge effects in UI layer, not post.
- **VFX:** GPU particle system (instanced quads, curl noise in shader, soft-particles), ribbon trails, ground decals (telegraphs, scorch, blood) via decal atlas + projected quads, screen shake manager with trauma model.
- **Budgets:** ≤ 300 draw calls combat scenes; ≤ 150 MB GPU textures via KTX2 (BasisU) compression; LODs on all monster/prop meshes; quality presets scale shadowmap, particle caps, post features.

## 6. World, Collision & AI

- **Zones:** authored as data (kit-piece placements + terrain heightfield + spawn tables + trigger volumes), loaded as chunks; streaming within an act, hard load between acts. Endgame Pathstones remix authored chunk-templates via seeded generation.
- **Collision:** 2.5D — circle/capsule agents vs. static edge-grid (from kit collider footprints) + heightfield stepping. Spatial hash for agent-agent (soft push) and hit queries (cone/arc/circle overlap tests in the same grid).
- **Pathing:** navgrid baked from collision at zone build; A* for single agents; **flow fields** per active combat cell for hordes (one field shared by a pack chasing the player). Pathing on a budget: staggered repath, worker-offload if profiling demands (Phase 6).
- **AI:** utility-lite state machines per family (idle/patrol → aggro → positioning → attack-select → recover), pack coordination tokens (max N simultaneous attackers), telegraph windup states that emit decal events.

## 7. Content & Data

- Every gameplay definition is typed data in `src/content/**` (TS objects with `as const satisfies Schema` — compile-time + runtime-validated).
- `tools/validate-content`: referential integrity (loot table → items, skill → VFX/SFX ids, quest → zones/NPCs), numeric sanity ranges, affix-pool exclusivity, rune×tag legality matrix. Runs as a Vitest suite; CI-fatal.
- Localization-ready: all player-facing strings through a string-table module from Phase 1 (English only shipped, but no hardcoded UI literals).

## 8. Save System (pre-MMO)

- IndexedDB, one DB, stores: `characters`, `account` (Ascension, stash, settings), `meta` (slots, versions).
- Every write is a versioned atomic snapshot (write-new-then-swap-pointer) with the 3 most recent kept as rolling backups; corruption → auto-fallback + user notice.
- **Migrations:** `save/migrations/vN.ts` chain, fixture saves per version committed in `tests/fixtures/saves/`, loader test loads every historical fixture to current.
- Export/import: single-file (JSON, gzip via CompressionStream) for user backup; format doubles as the Phase 7 account-import payload.
- Autosave: on zone transition, town entry, quest milestone, clean interval (60 s), and `visibilitychange`.

## 9. The MMO Boundary (why the retrofit is a port, not a rewrite)

These rules apply **from Phase 1**, cost little, and make Phase 7 tractable:

1. **Command-in, Event-out.** The sim is driven exclusively by a `Command[]` stream per tick (`Move`, `CastSkill{slot,aim}`, `Interact`, `UseItem`…) and communicates outward via events + read-only snapshots. In Phase 7 the same commands go over the wire and the same sim runs on the server.
2. **Deterministic sim** (§4) ⇒ client-side prediction is "run the same tick locally, reconcile on server snapshot."
3. **No client authority assumptions in content.** Loot rolls, damage math, and drops already flow through sim systems — never through UI/render code.
4. **Instanced-personal loot, party-size scaling hooks, and stagger/damage attribution** are designed multiplayer-safe now even though N=1.
5. **Ids & serialization:** entity/item ids are opaque and serialization-stable; item instances carry roll-provenance (seed + table id) enabling server-side re-validation later.

Full server architecture, protocol, and infra live in `docs/NETWORKING.md`.

## 10. Performance Engineering

- Frame budget (16.6 ms): sim ≤ 4 (amortized: 30 Hz sim on 60 Hz display = every other frame), render ≤ 10, UI/audio/other ≤ 2.
- **Zero-allocation hot paths:** SoA components, preallocated pools (projectiles, particles, damage numbers, events), no per-frame closures/arrays in systems; GC monitored in soak tests.
- Asset streaming: startup bundle ≤ 25 MB compressed (menu + first zone essentials); everything else lazy per-zone with priority queue + predictive preload of adjacent zones; KTX2 textures, Draco/meshopt-compressed GLB, OGG audio.
- Loading UX: named tips + zone art; never a frozen frame > 100 ms (chunked uploads to GPU).
- Diagnostics: in-game perf overlay (`F10`): fps, sim/render ms, draw calls, entities, GC; `?profile=1` boot flag records a startup trace.

## 11. Error Handling & Resilience

- Global error boundary: sim exceptions pause the game, snapshot state to IndexedDB (`crash-recovery` store), show a recover dialog; renderer exceptions attempt context-restore (WebGL context-loss handling mandatory).
- Structured logging (`debug` levels, ring buffer) exposed via `?debug=1`; Playwright asserts zero console errors on smoke paths.

## 12. Build, Deploy & CI Discipline

- `pnpm verify` = lint + typecheck + unit/content tests + build; `pnpm test:e2e` = Playwright against preview build. Both must pass before any push (see CLAUDE.md §3.5).
- Vercel: static output (`dist/`), SPA rewrite, immutable-hashed assets, brotli; `vercel.json` in repo. Preview per branch, production on main.
- Version + build hash shown on the main menu footer; CHANGELOG drives release notes screen in-game (Phase 6).
